## Must fix (6)

- [ ] **M6. The app crashes on any "called / named / titled" phrase** — `ReflexCore/Sources/ReflexCore/PayloadExtractor.swift:545-557` *(highest severity: a hard crash, found while writing tests, not from reading)*
  - **What this is:** `extractTitle` builds a regex with **three** capture groups, then reads group 3 and group 5: `match.range(at: 3)` and `match.range(at: 5)`.
  - **Problem:** `range(at: 5)` on a three-group pattern is out of range, and `NSTextCheckingResult.range(at:)` raises an Objective-C `NSException` that Swift does not bridge to an error. The process is terminated — no `try`, no log, no recovery. `extractTitle` is called for **every** transcript (`PayloadExtractor.swift:147`), so any utterance containing `called` / `titled` / `named` / `that says` crashes Reflex.
  - **Also wrong in the same function:** the group it *does* read (`at: 3`) wraps the verb with the payload, so even on a non-crashing phrase the title would come out as `"called q3 report"` rather than `"q3 report"`.
  - **Fix:** make the payload its own capture group and read that index, e.g. `(?:called|titled|named|that says|that is called)\s+(?:"([^"]+)"|([^.,!?;]+))` and use groups 1/2. Guard any index with `regex.numberOfCaptureGroups` if the pattern can change.
  - **If we skip it:** "new note called shopping", "create a file named q3", "open the document titled report" all terminate the app instantly.
  - **Evidence:** `reflex-cli --plan "new note called shopping"` → `NSInvalidArgumentException: ... rangeAtIndex: index 5 out of range` → `signal code 6`. Reproduced identically inside `swift test`.

- [ ] **M1. `runTool` deadlocks and permanently deafens the app** — `ReflexCore/Sources/ReflexCore/ActionDispatcher.swift:947-966`
  - **What this is:** `runTool` calls `process.waitUntilExit()` (line 955) and only then reads the child's stdout pipe (line 956).
  - **Problem:** A child that writes more than the ~64 KB pipe buffer blocks on write; the parent blocks forever in `wait()`. Reachable from `fileOperation` (line 575, "search for X and copy the path"). Because `dispatch` runs in `Task.detached` and `processing = false` only happens after it returns (`AppModel.swift:334,363`), the app then drops every later segment as "Busy" until relaunch — no crash, no log.
  - **Fix:** drain the pipe before waiting (`readDataToEndOfFile()` then `waitUntilExit()`), or use `readabilityHandler`.
  - **If we skip it:** one unlucky voice command hangs the app for good.
  - **Evidence:** `mdfind -onlyin / invoice` → 160 KB, `test` → 2 MB; reproduced the exact ordering in Python → `HUNG`.

- [ ] **M2. The main thread freezes up to 3 s on every speech segment** — `Reflex/AppModel.swift:325` + `ReflexCore/Sources/ReflexCore/NowPlaying.swift:53-94`
  - **What this is:** `handleSegment` is `@MainActor` and calls `NowPlaying.status()`, which does two `semaphore.wait(timeout: .now() + 1.5)` calls.
  - **Problem:** Worst case 3 s of blocked main thread per segment. It runs *before* the `guard !processing` check, so even segments that are immediately discarded pay the full cost. While an action runs (e.g. an 8 s web-search wait) every utterance in between stalls the UI.
  - **Fix:** move the media check below the `processing` guard and off the main actor (or cache the status with a short TTL).
  - **If we skip it:** the window beachballs during normal use, exactly while the user is talking to it.

- [ ] **M3. The rule router sends commands the dispatcher cannot run, or runs the wrong one** — `RuleRouter.swift:56,136,159-161,201,226-230` + `ActionDispatcher.swift:466-502`
  - **What this is:** Live `--rule` probes plus code read:
    - `"turn off the screen"` → `system_control`, but `systemControl` has no "turn off"/"screen" branch → throws `parseFailure`. This is the *only* display-sleep phrase that even reaches `system_control`.
    - `"turn off the display"`, `"sleep the display"`, `"put the display to sleep"` → `media_control`, because `RuleRouter.swift:56` uses `t.hasSuffix("play")` and "display" ends in "play". So the router's own display-sleep rule (`RuleRouter.swift:159-161`) is unreachable for three of the four phrases it lists, and `mediaControl` (`ActionDispatcher.swift:241`) then picks `contains("play")` → **starts playing music** instead of sleeping the display.
    - `"open the display"` → `media_control` for the same reason. Any phrase ending in "display" is treated as a play command.
    - `"show desktop"` / `"show the desktop"` / `"go to the desktop"` → `open_folder`, because `isFolderOpen` (`RuleRouter.swift:136`, defined at 226-230) runs before the system block. So `ActionDispatcher.swift:476-478` (`show_desktop`) is dead for those phrases, and the user gets a Finder window instead of Show Desktop. Only `"reveal the desktop"` reaches it.
    - `"unlock the screen"` → `system_control` → `systemControl`'s `contains("lock")` → **locks the screen**. The router matches it because `"unlock the screen"` literally contains `"lock the screen"`.
    - `"open google chrome"` → `web_search`, because `RuleRouter.swift:201` matches a bare `"google"` before the `open_app` rule — see S8.
  - **Problem:** Five router phrases can never do what they say; several do a destructive opposite (unlock locks, sleep-the-display plays music). The `--rule` table and the dispatcher's branch table are two lists of phrases that must agree, and they disagree.
  - **Fix:** replace the `hasSuffix("play")` / `contains("play")` substring tests with word-boundary matches; align `systemControl`'s branches with the router's phrases; move the desktop rules above `isFolderOpen`, or delete the unreachable branches; require a word boundary for `lock` so `unlock` is not a lock.
  - **If we skip it:** common display/desktop/unlock commands fail with "Execute failed", start playing music, or lock the screen when asked to unlock it.
  - **Evidence:** `reflex-cli --rule` output recorded above; `ActionDispatcher.systemOperation(for:)` is now unit-tested (`ActionDispatcherTests.swift`), and the mismatches are pinned as `withKnownIssue` cases.

- [ ] **M4. `type_text` and `new_item` press a keystroke before the target app is frontmost** — `ActionDispatcher.swift:329-345`, `414-443`
  - **What this is:** Both call `NSWorkspace.shared.open(url)` and then immediately `pasteText` (⌘V) or ⌘N. There is no wait, no `activate`, no polling for frontmost (grepped the dispatcher and `ShortcutController`).
  - **Problem:** App launch/activation takes ~0.5–2 s. The keystroke lands in Reflex or the previously frontmost app. This is the headline feature ("type buy milk in notes").
  - **Fix:** after opening, poll `NSWorkspace.shared.frontmostApplication` (or `activate()` + wait) with a short timeout before sending the keystroke.
  - **If we skip it:** dictated text silently goes to the wrong window or nowhere.

- [ ] **M5. Feedback muting destroys the user's mic level and does not actually mute** — `ReflexCore/Sources/ReflexCore/MicMute.swift:15-33` + `Reflex/AppModel.swift:461-467`
  - **What this is:** `muteInput(_, false)` writes a hardcoded `1.0`; the previous level is never read or restored. `withInputMuted` enables the mute, runs `NSSound.play()`, then unmutes in a `defer`.
  - **Problem:** Two bugs. (a) Every command resets the microphone input volume to 100%, silently changing system state the user set. (b) `NSSound.play()` is asynchronous, so the `defer` unmutes in the same run-loop tick — the mute window is ~0 ms, contradicting the header comment that calls this "the only thing that actually removes the sound from the microphone path".
  - **Fix:** read and restore the actual pre-mute scalar; hold the mute for the sound's duration (delegate/completion, or `play(untilDone)`).
  - **If we skip it:** every command stomps the user's mic gain, and the mechanic the file exists for does nothing.

## Should fix (10)

- [ ] **S1. Speech becomes a shell command with no confirmation** — `ActionDispatcher.swift:587-609`
  - **What this is:** `setupEnvironment` strips a leading verb and runs the rest in Terminal via `do script`.
  - **Problem:** The residual is never checked for being a plausible command. `"open a terminal"` routes to `environment_setup` (confirmed with `--rule`), "open " is stripped, and Terminal is told to run `a terminal` → "command not found". A mis-transcribed destructive phrase runs with no confirmation.
  - **Fix:** refuse to run when the residual is not a plausible command (e.g. a leftover leading article), and show/confirm the command for this target.
  - **If we skip it:** a normal request produces error noise, and the one path that executes arbitrary text has no guard.

- [ ] **S2. "Wait for search results" cannot fail and its result is thrown away** — `ActionDispatcher.swift:226` + `BrowserController.swift:583-630`
  - **What this is:** The poll returns `true` as soon as one visible `<a href>` exists (nav/footer links satisfy that on the first poll). The caller does `_ =`. The `catch` returns `true // permissive`.
  - **Problem:** A gate that cannot fail, a return value nobody reads, and up to 8 s of dead time holding `processing` (all speech dropped meanwhile).
  - **Fix:** delete the call and the now-unused `waitForLoad`, or make the "open the first result" clause own the wait and use its boolean.
  - **If we skip it:** a variable multi-second pause after every web search that buys nothing.

- [ ] **S3. A second screenshot in the same minute overwrites the first** — `ActionDispatcher.swift:454-464`
  - **What this is:** The filename uses `DateFormatter.localizedString(... .short)`, which has minute granularity.
  - **Problem:** Two screenshots in one minute produce the same path; `screencapture` overwrites. The first shot is lost with no error.
  - **Fix:** add seconds (or a short epoch/UUID suffix) to the filename.
  - **If we skip it:** silent loss of the user's first screenshot.

- [ ] **S4. A bulk move reports success when it moved nothing** — `ActionDispatcher.swift:766-774`
  - **What this is:** The Finder AppleScript's result is discarded, and the matcher keeps the article ("move the invoices into archive" → matcher "the invoices", line 574).
  - **Problem:** `whose name contains "the invoices"` usually matches zero items, yet the action returns "Moved matching items into X".
  - **Fix:** return the moved count from the AppleScript and report it; strip a leading article from the matcher.
  - **If we skip it:** the user is told work was done that was not.

- [ ] **S5. "Find X and copy the path" is a no-op while the router says it should work** — `ActionDispatcher.swift:571` + `RuleRouter.swift:158-167`
  - **What this is:** The router accepts `search`/`find`/`locate` for `file_operation`; the dispatcher's search branch requires the literal word `"search"`.
  - **Problem:** "find my invoice and copy the path" routes fine, then hits `return .noOp("file operation not recognized")`.
  - **Fix:** use one shared predicate on both sides.
  - **If we skip it:** the phrase the router advertises silently does nothing.

- [ ] **S6. "Unmute" jumps the volume to 50%** — `ActionDispatcher.swift:666-668`
  - **What this is:** `.unmute` calls `setVolume(50)`.
  - **Problem:** The previous level is discarded. Volume at 10% → "unmute" → 50%.
  - **Fix:** remember the level before muting (or read `output muted` and restore) instead of a hardcoded 50.
  - **If we skip it:** the user's carefully set volume is replaced by an arbitrary one.

- [ ] **S7. Feedback mute hits the wrong device** — `Reflex/AppModel.swift:462` + `MicMute.swift:42-46`
  - **What this is:** `withInputMuted(nil)` resolves to the *default* input device, but capture may use `selectedMicID` (`AppModel.swift:251`).
  - **Problem:** With a non-default mic selected, the device actually recording is never muted, so the feedback ding is still captured. The feature is silently defeated.
  - **Fix:** pass `selectedMicID` (as `UInt32`) into `withInputMuted`.
  - **If we skip it:** the feedback tone gets transcribed as speech for anyone not on the default mic.

- [ ] **S8. "Open <browser> by name" is hijacked into a web search** — `RuleRouter.swift:201`
  - **What this is:** The web-search rule accepts a bare `t.contains("google")` and is evaluated before the `open_app` rule. Confirmed with `--rule`: `"open google chrome"` → `web_search`.
  - **Problem:** You cannot open Chrome (or any app whose name contains a site name — Google Chrome, GitHub Desktop) by voice; you get a Google search for "chrome" instead.
  - **Fix:** require the site token to be adjacent to a search verb, or let a leading `open`/`launch` verb win over the bare site check.
  - **If we skip it:** a whole class of app names is unreachable by name.
  - **Evidence:** `reflex-cli --rule "open google chrome"` → `web_search (conf 0.85)`; pinned as a `withKnownIssue` case in `RoutingContractTests.swift`.

- [ ] **S9. A compound command silently drops a trailing "and press enter"** — `CompoundRouter.swift:38-56`
  - **What this is:** When the tail after a connective is only "press enter", the splitter does `text = left; break` (`CompoundRouter.swift:40-43`) and returns the truncated part list. The folded submit is never written to any `Part.submit`.
  - **Problem:** The doc comment on `CompoundRouter` promises "a trailing 'and press enter / hit submit' folds into the *previous* part's `submit` flag". It does not. Confirmed with `reflex-cli --compound "open notes and type buy milk and press enter"` → clause 2 is `type buy milk`, `submit` false. The user's text is typed but never sent.
  - **Fix:** capture the trailing submit text and set `submit: true` on the last part before returning.
  - **If we skip it:** every dictation ending in "and press enter" types the message and stops.
  - **Evidence:** `--compound` output above; pinned as a `withKnownIssue` case in `CompoundAndGatingTests.swift`.

- [ ] **S10. Payload text containing "and" is split mid-sentence** — `CompoundRouter.swift:81-97`
  - **What this is:** `looksLikeActionStart` returns true when the left clause merely *starts* with a command verb. For `"type this and that"` the left clause `"type this"` starts with `type `, so it splits — even though the source comment says that exact phrase "must not split, because its left side is mid-payload".
  - **Problem:** Confirmed with `--compound "type this and that"` → 2 clauses, `["type this", "that"]`. The typed payload loses everything after "and". Same for `"search for cats and dogs"`.
  - **Fix:** do not split when the text before the connective is an in-progress payload for a verb that consumes free text (`type`/`write`/`dictate`/`search for`/...), or split only on the payload boundary.
  - **If we skip it:** dictated text and search queries are silently truncated at the word "and".
  - **Evidence:** `--compound` output above; pinned as a `withKnownIssue` case in `CompoundAndGatingTests.swift`.

## Verdict

Two tables of phrases that must agree — `RuleRouter` and `ActionDispatcher` —
and they already disagree in six places, five confirmed against the live binary;
that remains the structural weakness. The worst issue is now a hard crash
(**M6**): `extractTitle` reads a capture group that does not exist, so any
"new note called …" terminates the process. The `runTool` pipe deadlock (M1) is
the worst non-crashing bug; the type-text race (M4) and the mic-volume stomp
(M5) are the ones users will notice daily. Beyond S1's unguarded shell path
there is no data-loss or security hole, and the compound drop/truncation bugs
(S9, S10) silently discard dictation text.

**Priorities:** M6 (crash) → M1 (deadlock) → M3 (misroutes) → the rest.

**Lean: −90 lines, −2 dependencies possible.** Dead declarations in N1, plus
`accelerate` and `protobuf` in `tools/requirements.txt` are imported by no tool
(they still arrive transitively, so the explicit lines can go).
